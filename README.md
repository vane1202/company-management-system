# 公司内部管理系统

运营、拍剪、客服各自登录填报，客服主管查看负责小组的加粉汇总，Boss / 行政查看全局经营估算与详情。界面为中文，适配手机和电脑。

本仓库是可运行的第一版，用于受控内网或限定 IP 内测。尚未购买或连接云服务器，也没有真实客户数据。

## 已实现

- 账号密码登录、角色权限、会话 Cookie、CSRF 与 Origin 校验、登录限速、密码哈希
- 不开放注册；管理员通过页面或 `npm run init-admin` 创建账号，无默认生产密码
- 客服加粉：同一 H5 入口；默认东八区业务日；员工+日期唯一；重报覆盖并留痕；`0` 与未报区分；默认近 3 个业务日可补报（服务端强制，可在后台设置）
- 成员小组归属按生效区间记录，调组不改写历史日报
- 客服主管只看授权小组的加粉总数、应报/已报/未报、逐人明细和导出；不能看工资、订单、消费和成本
- 运营日报（推广费、推广视频数）、拍剪日报（拍摄/成片/已发布/囤量快照）
- 客服订单：业务日、订单标识去重、金额与成本明细；不采集手机号等联系方式字段
- 岗位月基本工资按生效区间维护，按当月天数分摊，不需要每天录入
- Boss 日/周/月经营估算：收入 − 退款 − 推广费 − 工资分摊 − 定制成本 − 工费 − 运费（收入含期内全部订单金额，再减去状态为退款的订单金额；明确标注不是会计净利润）
- 后端强制数据范围，导出跟随同一权限
- 审计日志不记录密码

- 未配置国内 OSS 加密备份，因此**不能声称已经具备加密备份**。`scripts/backup.sh` 仅做本地明文 `pg_dump`

- Boss 批注目前仅本人/行政可见完整列表，尚未做成「对应端口自动可见」的通知

## 本地启动

需要 Node.js 20+ 和 PostgreSQL 16+（推荐 Docker Compose）。更完整的前提、回滚、备份恢复和验收清单见 [docs/LOCAL_DEPLOY.md](docs/LOCAL_DEPLOY.md)。该文档是部署准备，不代表已经部署或验收完成。

```bash
cp .env.example .env
# 编辑 .env：填写 DATABASE_URL、SESSION_SECRET、POSTGRES_PASSWORD
# 不要把填好的 .env 提交到 Git

# 启动前只读预检。默认不读取 .env；只有显式指定文件时才检查该文件。
# 预检不会安装软件、改库、跑迁移或启动服务，也不能代替任何启动脚本。
npm run preflight -- --env-file .env

docker compose up -d db
# 或使用已有 PostgreSQL，并把 DATABASE_URL 指过去（本项目示例端口 15432）
# 可选：npm run preflight -- --env-file .env --check-db

# 正式或可复现安装优先使用锁定文件：
npm ci
# 日常开发也可以 npm install
npm run migrate
npm run init-admin
# 交互输入管理员账号，或设置：
# INIT_ADMIN_USERNAME=... INIT_ADMIN_PASSWORD=... INIT_ADMIN_NAME=... npm run init-admin

# 开发：后端 http://127.0.0.1:13080 ，前端 http://127.0.0.1:15173
npm run dev
```

浏览器打开 [http://127.0.0.1:15173](http://127.0.0.1:15173)。前端开发服务器会把 `/api` 代理到后端。

生产式本地预览（前端打包后由后端一起提供）：

```bash
npm run build
SERVE_STATIC=true npm run dev:backend
# 然后访问 http://127.0.0.1:13080
```

演示数据默认不写入。若需要虚构账号，显式执行：

```bash
SEED_DEMO=1 npm run seed-demo
```

脚本把虚构账号写入 `SEED_DEMO_CREDENTIALS_FILE` 指定的本地文件（未设置时为 `data/demo-credentials.txt`），终端只显示用户名和角色，不打印密码。这些账号不是真实员工。

## 经营估算口径（最小可解释模型）

当前订单只有一条记录和一个 `status`，没有独立的退款日期、部分退款金额或成本冲回字段。估算按以下规则，便于对账，不是完整会计准则：

- **收入**：查询期内全部订单的 `amount` 之和（包含状态为退款的源订单）。
- **退款**：同期 `status = refunded` 的订单 `amount` 之和。
- **估算**：收入 − 退款 − 推广费 − 工资分摊 − 定制商品成本 − 工费 − 运费。
- 因此，一笔先成交再被改成退款的订单会同时出现在收入和退款中，净额为 0，而不会先从收入里消失再扣一次退款。
- 举例（待业务确认历史口头数字时，按同一规则解释）：若有成交 1280、560，另有一笔状态为退款的 90，则收入 = 1930，退款 = 90，收入 − 退款 = 1840。若把 1280+560=1840 当作已排除退款后的收入，再减 90，会把同一笔退款扣两次。系统不采用后一种算法。
- 局限：退款订单的定制成本、工费、运费仍计入；没有部分退款；订单始终按录入的 `business_date` 归属，把状态改成退款不会自动记到“退款当天”。若以后要按退款发生日或净额口径出报表，需要先明确业务定义再改模型。
- 工资按自然月天数分摊；某一区间完整覆盖某自然月时，该月合计等于月基本工资。同一员工的工资区间由数据库禁止重叠。
- 囤量取查询期内每人最后一条快照再相加，不把每日快照当作产量求和。

## 权限摘要

| 角色 | 可写 | 可读 |
| --- | --- | --- |
| 运营 | 本人推广日报 | 本人推广数据 |
| 拍剪 | 本人拍摄/成片/囤量 | 本人拍剪数据 |
| 客服 | 本人加粉、本人订单 | 本人加粉和订单 |
| 客服主管 | 本人加粉；可在授权组内代为更正加粉并留痕 | 授权组加粉汇总，不能看工资/订单/成本 |
| 助理 | 审核运营/拍剪/加粉/订单：通过或退回（退回须填原因），不能改业务数字 | 日常填报的待审/退回/通过列表；不能看工资、工资推算或经营估算 |
| Boss / 行政 | 编制、工资、设置；可查看并维护全局业务数据 | 全局汇总与详情；日常指标按待审/退回/通过分开展示，工资为整体成本 |

篡改 URL 中的 `userId` / `teamId` 会被后端拒绝。

## 安全注意

- 生产环境必须使用足够长的随机 `SESSION_SECRET`，并通过 HTTPS 将 `COOKIE_SECURE=true`
- 内测若只在 HTTP 上访问，不要录入真实客户或真实工资数据
- `TRUST_PROXY` 仅在前面确有反向代理时开启
- 登录有频率限制；首次由行政创建的账号会要求修改密码

## 审核与升级

- 角色 `assistant` 在界面中显示为「助理」。助理审核运营、拍剪、加粉和订单，不能修改业务数值，不能管理人员或改角色，也不能查看工资和经营估算。
- 员工新提交或修改日常数据后进入待审；助理通过或退回（退回必须填写原因）。已审核数据被改动后会重新待审，并用版本号阻止审核旧版本。
- 升级请先备份数据库，再执行 `npm run migrate` 应用 `002_review.sql`。已有日常数据会保持为待审，不会自动变成已通过。
- Boss 手机端可切换待审/退回/通过查看日常汇总；默认展示已通过，但必须能查看全部状态。工资没有审核状态，按整体成本单独展示，不会拆进三个状态以免重复扣减。整体经营估算仍按原口径计算全部日常数据减去整体工资，并明确标注它不是某一审核状态的净利润。
